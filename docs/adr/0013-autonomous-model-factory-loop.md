# ADR-0013 자율 모델 팩토리 반복 (Factory Loop)

상태: 채택 (2026-11-28)

## 배경

사람이 2026-11-28에 다음을 지시했다. HIVEMIND가 반도체 설계·제조에 쓰일 모델의 후보를 찾고, 조사와 브레인스토밍으로 과제를 고르고, 학습하고, Hugging Face에 배포하는 일을 사람 개입 없이 반복한다. 목표는 산업 현장에서 쓰일 수준의 모델과 Hugging Face에서의 인기다. 같은 날 사람이 정한 조건은 네 가지다.

1. 공개는 자동으로 한다. 학습 전에 고정한 합격 기준, 독립 검증기, 라이선스·비밀값 검사를 모두 통과하면 사람 승인 없이 공개하고, 하나라도 실패하면 공개하지 않는다.
2. GPU 총상한 1,000 USD(Silicon Model Factory 장부와 HIVEMIND 중앙 원장)를 유지하고, 과제 하나에 GPU 150 USD까지만 쓴다. 예산이 바닥나면 반복을 멈추고 알린다.
3. 조사·선정·코드 작성은 HIVEMIND 클라우드 워커가 한다.
4. 앞서 조사한 RTL 생성·수리 과제를 첫 후보로 넣는다.

지금 HIVEMIND에는 코드 작성(전달 작업), 학습(Model Factory), 독립 검증, Hugging Face 게시가 있다. 그러나 이를 정해진 순서로 계속 진행시키는 주체가 없고, 공개 승인과 게시는 운영자 토큰이 필요하며, 워커에는 Python과 Model Factory 저장 공간 권한이 없고, Hugging Face 저장소는 미리 만들어 두어야 한다.

## 결정

Control Plane 안에 **Factory Loop**를 둔다. Factory Loop는 하나의 상태 기계이고, 상태는 Aurora DSQL에 둔다. Control Plane은 Fargate Spot에서 상시 실행되므로(2026-11-27 결정) 주기 타이머로 루프를 한 단계씩 진행한다. Spot 회수로 Control Plane이 바뀌어도 상태가 DSQL에 있으므로 다음 작업이 이어서 진행한다.

### 한 주기(cycle)의 단계

| 단계 | 하는 일 | 실행 주체 | 산출물 |
|---|---|---|---|
| `research` | 후보 조사와 브레인스토밍. 출처: Hugging Face 반도체 관련 인기 모델·데이터셋, NVIDIA·삼성·SK하이닉스의 연구·관심 분야, 이전 주기의 결과와 다운로드 수 | 워커(모델 CLI) | 후보 목록 JSON(근거 URL 포함) |
| `select` | 정해진 채점표로 후보를 비교하고 하나를 고른다 | 워커 + Control Plane 검사 | 선정 결과와 이유 |
| `design` | 데이터 구축·학습·평가 코드, 기준 모델, 테스트셋, 합격 기준(`criteria.json`), 모델 카드 초안을 만든다 | 워커 | 과제 묶음(S3) |
| `build` | 데이터 구축과 기준 모델 측정 | Model Factory 작업(CPU 또는 GPU 스팟) | 고정 입력 묶음, 기준 수치 |
| `train` | 학습과 테스트셋 평가 | Model Factory 작업(GPU 스팟) | 산출물과 영수증 |
| `verify` | 합격 기준, 라이선스, 비밀값 검사 | 독립 검증기 | 검증 결과 |
| `release` | Hugging Face 공개 저장소 생성과 게시 | Control Plane | 공개 모델 |
| `observe` | 공개한 모델의 다운로드·좋아요 수 수집 | Control Plane | 다음 `research`의 입력 |

실패한 단계는 정해진 횟수만큼 다시 시도하고, 그래도 실패하면 그 과제를 `abandoned`로 닫고 다음 주기로 간다. 주기마다 결과를 Silicon Model Factory 저장소의 기록과 HIVEMIND 이벤트에 남긴다.

### 안전 장치

- **예산.** 학습과 데이터 구축의 Model Factory 작업은 지금처럼 중앙 원장의 예약을 통과해야 실행된다. Factory Loop는 과제별 누계가 150 USD를 넘는 작업을 등록하지 않는다. 남은 총예산이 다음 작업의 최대 비용보다 작으면 루프를 `paused_budget`으로 멈추고 알린다.
- **합격 기준 고정.** `criteria.json`과 테스트셋 해시는 `design` 단계 끝에 정하고, 학습 승인 지문에 들어간다. 그 뒤에는 바꿀 수 없다.
- **자동 공개 조건.** Control Plane이 공개하려면 네 가지를 모두 만족해야 한다. 독립 검증기가 합격 기준 통과를 기록했다(`independent_verifier`). 데이터셋과 기반 모델의 라이선스가 허용 목록(Apache-2.0, MIT, BSD 계열, CC0, CC-BY)에 있다. 산출물에서 비밀값 검사가 통과했다. 저장소 이름이 정해진 조직과 접두사 규칙을 따른다. 운영자의 수동 공개 승인 경로는 그대로 둔다.
- **중지 스위치.** 운영자는 API와 MCP로 루프를 멈추거나 다시 시작할 수 있다. 에이전트 토큰은 루프를 조회만 한다.
- **외부 활동 제한.** 루프는 Hugging Face 공개와 자기 저장소 기록 외의 외부 활동(커뮤니티 게시글, 다른 프로젝트 이슈)을 하지 않는다.

## 구현 순서

1. 루프 상태 저장소, 진행 타이머, 운영자 API·MCP(조회, 중지, 재개). 단계 실행기는 꽂아 넣는 구조로 둔다.
2. 워커의 단계 실행 모드: 프롬프트와 입력을 받아 모델 CLI를 실행하고 결과 JSON을 S3 `factory/`에 쓴다. 워커 이미지에 Python을 넣는다.
3. `research`·`select`·`design` 단계 연결.
4. `build`·`train`을 Model Factory 작업으로 연결하고 과제별 예산을 강제한다.
5. 자동 공개 정책과 Hugging Face 저장소 생성.
6. `observe`와 다음 주기로의 되먹임.

## 결과

사람은 루프의 상태 조회와 중지만 하면 된다. 비용은 기존 원장과 과제별 상한으로, 공개는 고정 기준과 독립 검증으로 통제한다. 대신 모델 CLI의 판단 품질이 과제 품질을 정한다. 조사가 틀리면 쓸모없는 모델을 학습해 예산을 쓸 수 있으므로, 과제별 상한이 손실의 상한이다. 자동 공개는 공개 전 사람이 결과를 보지 않는다는 뜻이므로, 모델 카드에는 측정한 수치와 한계만 쓰게 하고 검증기가 카드의 수치를 영수증과 대조한다.
