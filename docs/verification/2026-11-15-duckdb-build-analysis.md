# DuckDB 빌드 시간 차이 분석

로컬 2워커 × 컴파일 동시성 5와 Cloudflare standard-4의 4워커 × 컴파일 동시성 4를 비교했다. 두 조건 모두 3/3 완주했다. 전체 중앙값은 로컬 1,227.807초, 원격 1,415.612초다. 원격이 187.805초, 15.3% 오래 걸렸다. 구성별 중앙값은 개별 실행을 요약하며, 아래의 블록별 시간 분해는 실제 같은 블록의 두 실행을 대조한다. [본실험 결과](2026-11-15-duckdb-main-results.md)

## 구성별 측정

| 구성 | Unity / Assert | 로컬 빌드 벽시계(초) | 원격 빌드 벽시계(초) | 로컬 빌드 CPU초 | 원격 작업 CPU초 |
|---|---|---:|---:|---:|---:|
| C1 | 켬 / 끔 | 329.7 | 561.9 | 1,220 | 2,253 |
| C2 | 켬 / 켬 | 323.9 | 542.2 | 1,191 | 2,179 |
| C3 | 끔 / 끔 | 887.0 | 1,318.7 | 3,240 | 5,270 |
| C4 | 끔 / 켬 | 880.7 | 1,302.3 | 3,213 | 5,205 |

빌드 벽시계는 컴파일·링크를 실행하는 명령의 시간이다. 로컬 CPU는 빌드 프로세스와 회수된 자식의 wait4 CPU 합계다. 원격 CPU는 입력 준비·설정·빌드·테스트를 포함한 cgroup 합계다. 범위가 다르므로 CPU 열을 빌드 전용 CPU의 정확한 비율로 사용하지 않는다. 원격 작업 CPU초는 보존된 Ninja 시간 합계에 가깝고, 기록된 CPU 스로틀링은 0이다. CPU초와 벽시계를 구분하며 vCPU의 단일 코어 성능은 여기서 분리할 수 없다.

|---|---:|---:|---:|---:|
| C1 | 1,629.6 | 4.5 | 2,242.0 | 517 / 584 |
| C2 | 1,596.8 | 5.6 | 2,163.5 | 517 / 584 |
| C3 | 4,424.1 | 5.6 | 5,265.7 | 1,876 / 1,943 |
| C4 | 4,389.8 | 6.0 | 5,198.0 | 1,876 / 1,943 |

Ninja 합계는 병렬 작업 간 중첩을 포함한다. 로컬 분류는 출력 확장자와 알려진 실행 파일 경로를 기준으로 한다. 원격은 전체 행 수와 시간 합계만 남아 있어 컴파일과 링크를 따로 복원할 수 없다. 로컬에서는 오브젝트 컴파일이 작업 시간 대부분을 차지했다. 원격에서 링크가 얼마나 기여했는지는 추가 계측이 필요하다.

같은 Git 소스와 테스트 목록에도 Ninja 작업 그래프는 달랐다. 원격은 모든 구성에서 67행 더 많았다. 고정 DuckDB 소스의 확장 설정은 Linux 64비트에서 jemalloc을 기본 로드한다. 그 구성에 C 오브젝트 65개, C++ 래퍼 하나와 정적 확장 라이브러리 타깃이 있어 관측된 차이와 부합한다. 원격 출력별 목록이 없어 추가 작업의 분류와 소요 시간은 아직 확인되지 않았다. 로컬은 arm64/macOS Apple Clang 21, 원격은 x64/Linux Debian Clang 14.0.6이었다. [DuckDB 고정 버전의 확장 설정](https://github.com/duckdb/duckdb/blob/68d7555f68bd25c1a251ccca2e6338949c33986a/extension/extension_config.cmake)

Cloudflare는 C3·C4를 승인 후 약 19~21초에 시작했다. 로컬은 C1·C2가 자리를 비운 뒤 약 287~414초에 시작했다. 블록 2에서는 원격의 조기 시작 이점이 느린 개별 빌드를 상쇄했고, 블록 1과 3에서는 상쇄하지 못했다. 원격 입력 복원은 네 작업 합계 중앙값 17.6초이고, 최종 집계 중앙값은 7.5초였다. 원격 CPU 스로틀링, 입력 복원, 최종 집계에 먼저 손대는 것보다 C3·C4의 빌드 시간을 줄이는 편이 이 실험의 납기에 더 직접적이다.

## 개선 순서

1. **먼저 원격 C3·C4의 단계별 근거를 추가한다.** Ninja 출력별 시작·종료를 컴파일, 아카이브, 링크, 생성으로 분류해 남긴다. 링크 타깃별 시간과 컴파일 상위 지연 파일을 집계한다. CPU는 빌드 전후 cgroup 차이로 따로 잰다. 워커별 복원·검사 시간과 실제 활성 병렬도도 유지한다.
2. **공통 빌드 그래프에서 남는 격차를 측정한다.** 양쪽에서 jemalloc을 끈 별도 대조 조건으로 C3·C4를 반복한다. 확장 목록·Ninja 작업 목록을 확인하고 가능한 범위에서 Clang·CMake·Ninja 버전을 맞춘다. 기존 Linux 기본 구성은 운영 비교 기준으로 유지한다. 결과로 jemalloc의 추가 비용과 나머지 플랫폼 격차를 구분한다.
3. **실제 개발 경로에서 C3·C4의 재작업을 줄인다.** 같은 구성의 반복 빌드에 컴파일 캐시를 붙여 따뜻한 캐시 성능과 캐시 준비·전송 비용을 별도 측정한다. 모든 변경에서 Unity-off 검사가 필요한지 검증 계약으로 판단한다. 필요한 경우 두 작업을 일찍 시작하고, 원격 워커당 컴파일 슬롯을 늘려 볼 때는 CPU·메모리·비용과 완료율을 함께 비교한다.
4. **링커 변경은 원격 링크 시간이 큰 것으로 확인된 경우에 평가한다.** 링크 교체가 대상 플랫폼과 검사 결과에 미치는 영향을 검증한다.

원자료는 `.hivemind/duckdb-pilot/runs/main-b*-local-c2-j5/`의 stage 결과와 Ninja 기록, 그리고 `.hivemind/duckdb-pilot/main-matrix/main-b*-cloud-c4-j4/build/result.json`이다. 이번 문서는 기존 3블록을 분석한 결과다.
