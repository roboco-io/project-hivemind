# 자율 반복 플랫폼 기능 실증 (이슈 #20)

2026-11-28에 실제 AWS(서울 Hub, us-east-2 학습 리전)와 Hugging Face, SMF 저장소에서 이슈 #20의 완료 조건 1-5를 확인했다. 배포한 코드는 `b2cc06f`이고, 실증 중 발견한 결함 두 가지를 고쳐 `d7f7fe1`, `398b10c`, `d459967`로 다시 배포했다. 실증 범위와 정리 방법은 Silicon Model Factory 세션과 미리 합의했다. 계정 ID와 토큰 위치는 적지 않는다.

문자 구독에는 `{"$or":[{"channel":["urgent"]},{"channel":[{"exists":false}]}]}` 필터를 걸었다. AWS Budgets의 예산 알림에는 `channel` 속성이 없으므로, 이 필터는 예산 알림도 문자로 보낸다. 이메일 구독에는 필터를 두지 않았다.

## 실증 중 고친 결함

**트리거 작업의 수용 명세 누락(`d7f7fe1`).** 전달 API는 작업을 만들 때 `acceptance/<작업>.json`을 S3에 올리지만, 트리거는 저장소에 직접 작업을 만들어 이 단계를 건너뛰었다. 그래서 첫 시험 작업의 검증기가 S3 404로 종료되고 작업이 `running`에 남았다. 트리거가 작업을 승인하기 전에 수용 명세를 올리도록 고쳤고, 그 작업은 취소했다.

**상시 운영 Control Plane에 새 이미지가 반영되지 않음(`398b10c`).** 작업 정의는 `latest` 태그를 쓰므로, 작업 정의가 바뀌지 않은 배포에서는 실행 중인 작업이 이전 이미지로 계속 돌았다. Control Plane이 0으로 쉬던 시절에는 확인 단계가 새로 켜서 문제가 없었다. 부트스트랩이 새 Control Plane 이미지를 올린 뒤 서비스가 켜져 있으면 강제로 새 배포를 하고 안정될 때까지 기다리도록 고쳤다.

**워커 이미지에 `curl` 없음(`d459967`).** 시험 워커는 Python 표준 라이브러리로 대신 호출했다. 이미지에 `curl`을 넣었다.

## 확인하지 못한 것

자동 공개 작업이 게시 실패 뒤 주기 점검으로 다시 게시되는 경로, Spot 회수 뒤 트리거가 이어서 동작하는 경로는 실제 AWS에서 일으켜 보지 않았다. 단위 테스트로만 확인했다. 비용은 `t3.micro` 시험 작업 2개의 정산값을 시간당 상한가로 계산한 추정이며, 실제 청구는 확인하지 않았다.
