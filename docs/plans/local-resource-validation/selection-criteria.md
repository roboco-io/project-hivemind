# 로컬 실행과 HIVEMIND 선택 기준

사용자는 로컬에서 작업을 지시하고 결과를 검토한다. 실행 위치는 작업 묶음의 의존성, 로컬 자원 여유, 통합 완료 시간과 허용 비용에 따라 정한다. 아래 수치 기준은 다음 비교 실험을 위한 초기 제안이며 실측 후 조정한다. 현재 자동 라우팅에 적용된 정책은 아니다.

## 선택할 상황

| 작업 상황 | 우선 선택 | 선택 근거 |
|---|---|---|
| 작은 수정, 사용자와 짧은 간격으로 확인하는 작업, 로컬 전용 장치·화면에 의존하는 작업 | 로컬 | 피드백 왕복과 환경 준비 비용이 작다. |
| 같은 파일·설계·컨텍스트를 연속 수정하며 로컬 자원에 여유가 있는 작업 | 로컬의 연속 세션 | 의존성 대기와 작업 인계 비용을 줄인다. |
| 공통 계약을 고정하고 구현·검증할 수 있는 독립 작업이 여러 개 준비된 개발 목표 | HIVEMIND 병렬 실행 검토 | 실행 가능한 작업을 클러스터에 배분해 통합 납기를 줄일 수 있다. |
| 빌드·테스트가 사용자 머신의 응답성을 크게 낮추거나 메모리·실행 시간 한도를 넘는 작업 | HIVEMIND | 사용자 머신의 자원을 확보하고 작업을 완료한다. |
| 승인 후 노트북 종료·네트워크 단절 중에도 진행해야 하는 장시간 작업 | HIVEMIND | 원격 조정과 결과 보존·재조회가 필요한 경우다. |
| 공유 설계가 아직 결정되지 않은 큰 작업 | 공통 계약 확정 후 다시 선택 | 작업별 입력·변경 범위·통합 테스트가 정해져야 병렬 실행을 평가할 수 있다. |

## 판단 순서

1. **완료 기준을 고정한다.** 같은 커밋, 과제 범위와 최종 통합 테스트로 비교한다. 로컬 선택지에도 머신에서 감당할 수 있는 동시 실행을 허용한다.
2. **원격 실행 가능성을 확인한다.** 필요한 저장소·런타임·접근 권한, 제공자 인증과 실제 동시 실행 한도를 확인한다. 사용 가능한 동시 실행 수로 계산한다.
3. **사용 목적을 선택한다.** 납기 단축, 로컬 자원 확보, 연결 단절 중 진행 중 어떤 효과를 원하는지 기록한다. 여러 목적을 선택할 수 있다.
4. **시간과 비용을 추정한다.** 과거 유사 작업의 중앙값과 범위를 사용한다. 근거가 부족하면 작은 대표 작업으로 오차를 측정한다.
5. **실행 후 결과와 비교한다.** 성공한 작업과 실패·재작업 비용을 함께 기록하고 다음 선택의 추정치를 갱신한다.

## 초기 판정 기준

| 목적 | HIVEMIND를 선택할 제안 기준 | 검증할 값 |
|---|---|---|
| 통합 납기 단축 | 같은 품질 기준에서 예상 원격 완료 시간이 로컬의 70% 이하이고 추가 비용이 사용자 예산 안에 있다. | 실제 승인→최종 통합 테스트 통과 시간, 완료율, 실패·재시도 포함 총비용 |
| 로컬 자원 확보 | 작업 중 로컬 응답 시간 p95가 유휴 기준의 2배를 넘고 사용자가 정한 절대 응답시간 한도도 초과하거나, 메모리 압박·지속적 스왑 증가·OOM이 작업을 제한한다. 원격 실행에서 같은 문제가 해소되고 요구 납기·예산을 충족한다. | 로컬 CPU 시간, 호스트 메모리 압박·스왑, 응답 시간 p95, 검증 완료 작업 수 |
| 작업 지속 | 승인 후 정한 단절 구간에도 작업·검증이 진행되고, 재연결 후 동일한 결과를 회수할 수 있다. | 서버 시각의 진행·검증 이벤트, 결과 해시, 중복 실행 여부, 회수 시간 |

30% 시간 절감과 2배 응답 저하는 실험용 제안값이다. 응답성의 절대 한도, 납기와 허용 추가 비용은 작업 시작 전에 사용자 요구에 맞게 정한다. 측정 오차가 크면 시간 절감 예상 범위도 함께 제시한다. 원격 조정과 제공자 인증의 실제 동시 실행 한도 때문에 병렬 가속이 제한될 수 있다.

납기, 비용, 자원·연속성 중 선택한 목적의 기준을 만족하는 가장 작은 워커 수를 우선한다. 원격 1·2·4개로 측정해 워커 증가가 통합 완료 시간을 실제로 줄이는지 확인한다.

## 시간·비용 계산

- 로컬 시간은 해당 머신에서 실행 가능한 동시 작업 수를 적용한 전체 작업 묶음의 완료 시간이다.
- 원격 시간에는 제출·컨테이너 준비·제공자 및 의존성 대기·실행·재시도·충돌 해결·통합 테스트·결과 회수를 포함한다. 병렬 작업은 실제 실행 일정의 벽시계 시간으로 계산한다.
- 시간 절감률은 `(로컬 시간 − 원격 시간) / 로컬 시간`이다.
- 추가 비용은 동일한 작업 묶음의 원격 총비용과 계측 가능한 로컬 비용의 차이다. 로컬 전력·장비 비용의 미계측 항목을 표시하고 모델 토큰과 인프라 비용을 각각 기록한다.
- 비용은 워커 실행 외에도 캐시 준비·보관·전송, 검증·통합과 실패 시도까지 포함한다. 절감 시간이 양수일 때 추가 비용을 절감 시간으로 나누어 시간당 비용을 제시한다.

예를 들어 준비된 독립 작업 4개가 각각 로컬에서 10분, 원격에서 15분 걸리고, 제출·통합에 총 3분이 든다고 가정한다. 로컬 동시 실행이 1개라면 총 40분이고 원격 4개는 18분이다. 로컬에서 2개를 동시 실행할 수 있다면 20분이므로 원격의 절감은 10%다. 실제 동시 실행 한도에 따라 같은 작업의 선택이 바뀐다. 이 수치는 설명용 가정이다.

## 현재 근거와 다음 검증

동일 명령의 설치·빌드·테스트는 standard-1에서 로컬보다 느렸고, standard-3 증설은 도구·채점 시간을 줄였다. 동일 모델 입력 재생에서는 큰 전송 지연 차이가 재현되지 않았다. lockfile과 맞는 npm 캐시는 설치 GET을 줄였지만 전체 pi 시간은 모델 작업량에 따라 달라졌다. 따라서 단일 pi 세션 최단 기록만으로 다음 작업의 실행 위치를 결정하기 어렵다. [기존 실험 기록](../../../cloudflare/backend/benchmark/README.md)

다음 실험은 로컬·원격 순차·원격 병렬에서 같은 의존성 있는 작업 묶음을 끝까지 실행한다. 통합 납기 30% 절감, 품질 기준과 예산 충족 여부를 확인하고 로컬 응답성·연결 단절 조건을 함께 검증한다. [실험 설계](experiment.md)

## 2026-11-14 실측 반영

작은 RealWorld 과제에서는 로컬을 우선한다. A의 최선 로컬은 34.13초, 원격 4개 병렬은 46.13초였다. B의 로컬 병렬은 60.10초, 원격 병렬은 109.05초였다. 원격 내부 병렬화는 빨라졌으나 로컬 대비 납기 단축 기준은 충족하지 않았다.

관제 조회 프로세스를 5분 종료한 C 3회에서는 모두 단절 중 원격 통합과 재조회 해시 일치를 확인했다. 따라서 연결 지속이 어려운 작업은 원격 실행을 선택할 근거가 있다. 데스크톱 앱·운영체제 종료 자체를 시험한 것은 아니다.

이 규모는 32 GiB 머신의 자원 부족 해소를 입증하지 못했다. 더 큰 실제 저장소에서 로컬 동시 실행 한계를 찾기 전까지 대규모 개발의 성능 우위를 일반화하지 않는다. [최종 실측 결과](../../verification/2026-11-14-resource-validation-final.md)
