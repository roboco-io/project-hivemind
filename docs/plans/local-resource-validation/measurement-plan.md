# HIVEMIND 적합 작업의 실측 계획

실행 현황(2026-11-14): 최종 조건 A 18/18, B 9/9, C 3/3 통과. 원격 지속성은 확인했지만 로컬 대비 납기 단축 기준은 충족하지 못했다. 첫 토큰·HTTP 요청 수·로컬 누적 CPU초 등 미확보 지표와 준비 단계 실패는 [최종 결과](../../verification/2026-11-14-resource-validation-final.md)에 구분했다.

로컬 머신은 작업 제출·승인·진행 확인·결과 검토를 맡고, Cloudflare 클러스터가 구현·검증·통합을 수행한다. 이번 계획은 [선택 기준](selection-criteria.md)의 통합 납기, 로컬 자원 확보, 연결 단절 중 진행을 실제 작업으로 평가한다. 표본 수와 수치 한도는 실행 전에 조정할 수 있는 제안값이다.

## 1. 검증할 작업

| 실험 | 고정할 작업 묶음 | HIVEMIND에 기대하는 효과 | 완료 증거 |
|---|---|---|---|
| A. 검증 작업 병렬화 | 완성된 앱의 독립 테스트 4개 샤드와 각 샤드의 빌드·DB fixture 초기화. 마지막에 전체 회귀 검사 | CPU·메모리를 쓰는 검증을 분산해 납기를 줄이고 로컬 응답성을 확보 | 4개 샤드 결과, 누락 없는 테스트 목록, 최종 통합 검사 |
| B. 실제 기능 개발 | 같은 RealWorld 앱의 게시글 목록 기능과 댓글 목록 기능을 독립 워커에 배정 | 구현·수정·검증을 동시에 진행해 전체 개발 납기를 줄임 | 두 diff, 작업별 수용 테스트, 전체 Hurl 및 추가 통합 검사 |
| C. 관제 연결 단절 | B의 승인된 원격 실행 중 관제 클라이언트를 종료하고 결과를 다시 조회 | 로컬 연결 상태와 독립적으로 원격 작업을 지속 | 단절 중 서버 이벤트, 동일 작업 ID와 결과 해시, 중복 실행 없음 |

A는 각 샤드에 서로 다른 테스트 ID·DB fixture를 할당한다. 병렬도에 관계없이 동일한 4개 샤드와 최종 회귀 검사를 수행한다. B는 게시글의 안정적인 정렬·페이지네이션과 댓글의 안정적인 정렬·페이지네이션을 구현한다. 정렬 키, 동률 처리, 잘못된 요청, 경계 페이지, 접근 권한은 공통 계약과 테스트로 미리 고정한다. 공유 schema·라우팅·타입 계약을 준비한 기준 커밋에서 시작하고, 허용 파일 경로를 분리한다.

현재 작은 RealWorld 앱이 자원 압박을 만들지 못하면 A는 계측·실행 검증으로 판정한다. 더 큰 실제 저장소 또는 현실적인 데이터 크기의 고정 fixture를 다음 표본으로 선정한다. 규모는 사전 실행에서 결정한 뒤 모든 비교 조건에 동일하게 적용한다.

## 2. 현재 기능과 준비 작업

현재 Scheduler는 모델 agent 최대 2개, compute 최대 4개이며 credentialId별 모델 실행을 직렬화한다. 통합 워크플로는 서로 다른 제공자의 워커 2개와 겹치지 않는 쓰기 경로를 요구한다. 이번 B는 Codex·Claude 각 1개로 고정한다. 각 작업에 배정된 제공자·모델·effort는 로컬과 원격에서 동일하게 유지한다. [스케줄러](../../../cloudflare/backend/src/scheduler.ts) · [워크플로 계약](../../../cloudflare/backend/src/workflow.ts)

실험 준비 항목은 다음과 같다.

- 실행 manifest에 입력 커밋·snapshot, lockfile, 계약·테스트 해시, 모델·CLI 버전, effort, 병렬도, 캐시 조건을 기록한다. 현재 snapshot 한도인 4 MiB·1,000파일 안에 입력 소스를 구성한다. 큰 테스트 데이터는 고정된 생성 규칙과 시드로 작업 환경에서 생성하고 양쪽 해시를 대조한다.
- A의 compute 작업 묶음 제출·집계와 B의 원격 순차 실행을 위한 동시 실행 상한을 중앙 스케줄러에서 지원한다. 상한은 해당 실험 작업 묶음에만 적용한다.
- 모델·effort를 명시적으로 고정할 수 있는 실행 인자와 실제 응답 증거를 확인한다. 현재 코드로 해당 설정을 보장할 수 없는 제공자는 이 준비 작업을 먼저 완료한다.
- 로컬에서 작업 프로세스 트리와 호스트 전체의 CPU·메모리·스왑, 관제 프로세스의 자원, 네트워크 바이트를 수집한다. 단일 프로세스의 최대 RSS와 호스트 메모리 압박을 각각 표시한다.
- 승인, 큐 진입, 컨테이너 준비, 작업 시작·종료, 검사, 통합, 결과 조회 이벤트를 저장한다. 실패에도 종료 코드·시그널·정제된 오류를 보존한다.
- 제공자별 동시 실행 한도를 확인한다. 실제 겹쳐 실행된 시간을 기록해 설정한 병렬도와 대조한다.

이 항목은 구현 준비 목록이다. 이전 벤치마크의 측정값은 출발점으로 활용한다. 모델 4개 병렬 실행은 현재 워크플로 계약과 인증 처리를 확장한 후 별도 검증한다.

## 3. 비교 조건과 실행 수

| 단계 | 비교 조건 | 반복 수 | 합계 |
|---|---|---:|---:|
| 사전 계측 | 로컬 유휴·단일 작업, 원격 단일 작업, 양쪽 수용 테스트 | 각 1회 | 결과에 따라 작업 규모와 상한 확정 |
| A | 로컬 동시 1·2·4개, Cloudflare 동시 1·2·4개 | 조건당 3회 | 작업 묶음 18회 |
| B | 로컬에서 가능한 병렬 실행, 원격 순차, 원격 2개 병렬 | 조건당 3회 | 개발 목표 9회 |
| C | 원격 2개 병렬, 관제 연결 단절 포함 | 3회 | 개발 목표 3회 |

B·C 한 번에는 초기 모델 작업 2개와 필요한 랄프 반복이 들어간다. 초기 모델 작업은 총 24건이며 반복·실패 비용은 추가 집계한다. A의 완료 수는 샤드 단위와 작업 묶음 단위를 모두 기록한다. B·C는 통합 테스트에 합격한 개발 목표 한 개를 완료 단위로 센다.

로컬 기준 병렬도는 A에서 사용자 머신의 응답성 한도 안에서 가장 빠른 설정으로 선택한다. B의 로컬 조건에서도 최대 2개 워커를 사용할 수 있다. 제공자 할당은 환경 간 일치시키고 작업·모델을 바꾸면 별도 실험으로 표시한다.

A는 3개 블록에서 여섯 조건의 순서를 고정된 난수 시드로 섞는다. B는 로컬→원격 순차→원격 병렬, 원격 순차→원격 병렬→로컬, 원격 병렬→로컬→원격 순차로 순서를 교차한다. 조건 간 실행은 겹치지 않는다. 각 반복은 새 코드 작업 공간·DB·모델 세션에서 시작한다.

## 4. 고정 환경

로컬 기준은 현재 M1 MacBook Pro, 논리 CPU 10개, 32 GiB다. OS·Node·패키지 도구·CLI 버전을 manifest에 기록한다. Cloudflare는 standard-3을 고정하고 실제 배치 지역을 기록한다. 워커 증설과 캐시 효과가 섞이지 않도록 주 실험의 npm 캐시는 각 작업 시작 시 빈 상태로 고정한다. R2 재사용은 후속 별도 조건이다. 모델 제공자의 프롬프트 캐시 적중량은 실제 값을 기록한다.

공통 계약 확정·수용 테스트 작성에 걸린 사람의 준비 시간도 기록한다. 작업 묶음의 비교 시간은 승인부터 시작하며, 프로젝트 전체 보고에서는 준비 시간과 결과 회수까지의 시간을 추가로 제시한다.

원격 클러스터에서는 모델 작업·검사·통합을 수행하고 로컬은 관제한다. 로컬 기준 실험에서는 동일한 구현·검사·통합을 해당 머신에서 수행한다. 로컬의 일상 작업 부하는 첫 비교에서 일정하게 유지하고, 추가 부하 조건은 별도 블록으로 측정한다.

## 5. 필수 측정값

| 구간 | 지표 |
|---|---|
| 전체 납기 | 승인→최종 통합 테스트 합격, 승인→결과 회수, 제한 시간 내 완주율 |
| 병렬 처리 | 목표 병렬도, 실측 동시 실행 수, 워커별 큐 대기와 실행 시간, 의존성 대기 |
| 사용자 머신 | 짧은 고정 명령 p50·p95, CPU 사용 시간, 호스트 메모리 압박·스왑 변화, 관제 프로세스 자원 |
| 워커 | CPU 사용·스로틀링, 메모리 피크, npm 설치·빌드·테스트 시간, 모델 요청·첫 토큰·완료 시간 |
| 품질·재작업 | 작업별 검사, 전체 회귀 검사, 범위 밖 diff, 통합 충돌·추가 랄프 회차·복구 횟수 |
| 네트워크·지속성 | 제출·조회·결과 전송량, 연결 단절 구간과 그동안 완료된 서버 이벤트 |
| 비용 | 모델 토큰·캐시 읽기, 컨테이너·R2·전송, 검증·통합·실패·재시도 비용 |

짧은 고정 명령은 유휴 상태에서 5분간 측정한 뒤 작업 중에도 같은 주기로 실행한다. 예시인 Node 시작 명령에 실제 사용자 작업의 대표 명령을 하나 추가해 측정한다. CPU는 순간 사용률과 누적 CPU초를 구분한다. 메모리는 프로세스 트리 RSS와 운영체제의 메모리 압박·스왑 변화로 확인한다.

## 6. 통과 기준과 중단 기준

- **납기 단축 제안 기준**은 원격 병렬의 통합 완료 중앙값이 로컬보다 30% 이상 짧고, 원격 순차 대비 가속률이 1보다 큰 것이다. 세 블록의 개별 시간과 범위도 제시한다.
- **품질 기준**은 동일 수용 테스트와 최종 통합 검사 통과, 계약 유지와 허용 쓰기 범위 준수다. 개선 판정에는 조건별 3/3 완주를 초기 목표로 둔다. 실패 조건에서는 완주 수와 시간 초과를 표시하고, 제한 시간 내 완료율을 우선 비교한다.
- **자원 확보 기준**은 로컬 실행에서 응답 시간 p95가 유휴의 2배와 사용자가 정한 절대 한도를 함께 초과하거나 메모리 압박이 생기는 조건에서, 원격 관제 시 해당 문제가 해소되는 것이다. 문제가 발생하지 않은 규모의 결과에는 그 범위를 표시한다.
- **연결 단절 기준**은 실행 승인 후 클라이언트 연결을 5분 끊었을 때, 그동안 원격 진행 이벤트와 최종 검증 근거가 남고 재연결 후 같은 작업 ID로 결과를 회수하는 것이다. 단절 전 완료됐으면 유효 표본에서 제외하고 계획한 횟수 안에서 더 긴 과제로 교체한다.
- **제안 시간 상한**은 compute 작업당 10분, 모델 작업당 20분, 통합 검사 10분, 개발 목표 전체 60분이다. 사전 실행의 규모에 맞춰 본실험 전에 확정한다.
- **제안 예산 배정**은 사전 실행에서 얻은 실행당 비용 범위로 A·B·C 각각의 총액을 산정하고 전체 지출 한도를 승인받는 방식이다. 기존 구독 실행의 추가 모델 비용이 0달러여도 구독 한도·크레딧 설정과 클라우드 비용을 확인한다.
- 로컬 메모리 압박이 위험 수준으로 지속되거나 작업 한도를 넘으면 해당 시도를 종료하고 한계 관측으로 기록한다. 강제 OOM을 목표로 부하를 늘리지 않는다. 인증·비용·격리 경계가 깨지면 작업 묶음을 중단하고 원인을 먼저 수정한다.

실패는 총비용과 완주율에 포함한다. 완주 시간 중앙값에는 완료된 작업만 포함하고 표본 수를 표시한다. 미완료 작업을 빠른 실행으로 계산하지 않는다. 표본 3회는 초기 선택 근거이며, 편차가 크거나 판정 경계에 걸리면 해당 조건의 반복 확대를 검토한다.

## 7. 연결 단절 검증 절차

작업이 원격에서 시작된 뒤 관제 클라이언트를 종료하고 실험용 네트워크 경로를 차단한다. 서버 측 이벤트 시각으로 단절 중 실제 진행을 확인한다. 5분 후 연결을 복원해 원래 작업 ID의 diff·로그·테스트 해시를 조회한다. 사용자 컴퓨터 전체 네트워크 제어가 필요한 경우에는 해당 조작을 별도로 확인한다. 이 시험의 관측 범위는 승인 후 작업 지속과 결과 회수다.

## 8. 실행 순서와 산출물

1. 입력 커밋·작업 샤드·공통 계약·테스트·manifest를 준비하고 로컬 수용 검사를 통과시킨다.
2. 계측기를 검증하고 사전 실행으로 작업 규모·시간 상한·예상 비용을 확정한다.
3. A의 18개 작업 묶음을 실행하고 로컬 병렬 기준을 선택한다.
4. B의 9개 개발 목표를 실행해 통합 완료 가속과 비용을 비교한다.
5. C의 3개 연결 단절 실행을 검증한다.
6. 조건별 개별 기록, 중앙값·범위·완주율, 병렬 가속률, 로컬 응답성, 완주당 비용, 권장 워커 수를 보고하고 선택 기준을 갱신한다.
